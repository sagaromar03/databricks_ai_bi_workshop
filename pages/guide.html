Concept

The Metric View

In one line: a metric view lets you define a number like Total Volume or VWAP once, in one central place, and then everything — dashboards, Genie, SQL — uses that exact definition instead of each re-inventing the formula.
📖
Think of it as the official rulebook for your numbers. Imagine ten people each work out “total revenue” their own way — you’d get ten slightly different answers and endless arguments. A metric view writes the rule down once: “revenue = this formula.” After that, everyone who asks for revenue gets the same number.
🧩

The problem it solves

Without it, every dashboard and analyst writes their own SQL for the same idea, and small differences make two reports quietly disagree.

One source of truth

Each metric’s formula lives in one place, so everyone gets the same number.

No repeated SQL

Define the joins and maths once; people just pick a metric and how to slice it.

Genie answers correctly

Ask “VWAP by country” and Genie uses the governed formula — it doesn’t guess.

Governed & consistent

It’s a normal Unity Catalog object, so permissions and lineage just work.

🔑

What’s inside: a source, dimensions & measures

A metric view points at a source to read from, then exposes two kinds of things on top of it — dimensions and measures.

Source

where the data comes from

The table (or view) the metric view is built on, plus any joins it needs. Ours reads from trade_enriched — trades already joined to their market price and EUR values — and joins out to the dimension tables (time, trader, counterparty, instrument, delivery point, market) so those fields are available to slice by.

Dimensions

the ways you slice
  • Trade Date, Trading Season
  • Trader Company, Counterparty
  • Commodity, Country
  • Direction (buy / sell)

Measures

the numbers, with their formula
  • Trade Count — COUNT(1)
  • Total Volume — SUM(volume)
  • VWAP — volume-weighted price
  • Total Notional EUR — value in EUR
🔀

Coming from Power BI?

If you’ve built Power BI models, a metric view will feel familiar — here’s the mapping.

In Power BIMetric view equivalent
Semantic model / datasetThe metric view itself — but a governed Unity Catalog object, not locked to one report
DAX measure — Total Sales = SUM(...)A measure — Total Volume: SUM(volume), written in SQL rather than DAX
Fields on axes & slicersDimensions
Model relationships + Power Query sourceSource + joins
Certified / shared datasetEvery tool — dashboards, Genie, SQL — reads the one definition
Q&A (natural language)Genie

The big shift: your measures live in the catalog, not inside a single .pbix — so a dashboard, a Genie agent, and a raw SQL query all return the identical number.

📄

What it looks like

It’s written in a short YAML file: a source, the dimensions, and the measures. A trimmed peek at this workshop’s energy_trading_metrics:

# energy_trading_metrics — written once, read everywhere
source: energy.energy_trading.trade_enriched

dimensions:
  - name: Trade Date
    expr: dt.cal_date
  - name: Commodity
    expr: di.commodity
  - name: Direction
    expr: source.direction

measures:
  - name: Total Volume
    expr: SUM(source.volume)
  - name: VWAP
    expr: SUM(source.price * source.volume) / NULLIF(SUM(source.volume), 0)
  - name: Total Notional EUR
    expr: SUM(source.notional_value_eur)
    format: { type: currency, currency_code: EUR }
📊

The measures in ours

MeasureWhat it means
Trade CountTotal number of trades
Total VolumeTotal traded volume (mixed units across commodities)
VWAPVolume-weighted average price
Buy Volume / Sell VolumeVolume split by trade direction
Total Notional EURTotal value of all trades, converted to EUR
Avg Pct vs MarketVolume-weighted distance from the market price (negative = below) — the surveillance signal

Where it’s used here

You don’t point tools at raw tables — you point them at the metric view, and they inherit every measure above.
