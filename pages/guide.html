Concept

Unity Catalog

In one line: Unity Catalog is the single place where all your data and AI assets live, get organised, and get secured — one governance layer that every workspace and tool shares.
🏢
Think of it as a well-run office building with a directory at the door. A catalog is a floor, a schema is a room on that floor, and a table is a filing cabinet in that room. Everything has one clear address, and the front desk (governance) decides who can open which door — instead of files scattered across everyone’s desks.
📍

The three-level name

Every object has a three-part address: catalog › schema › object. That’s why you’ll see names like this throughout the workshop.

catalogenergy. schemaenergy_trading. table / viewfact_trade
📦

What it holds

Not just tables — one catalog governs every kind of data & AI asset:

🗄️ Tables🔎 Views📐 Metric views 📁 Volumes (files)🧮 Functions🤖 ML models

Dashboards and Genie agents aren’t stored in Unity Catalog — they’re workspace tools that read from the governed data above.

🛡️

Why it matters

One permission model

Grant access once with GRANT; it applies everywhere, for every tool.

Lineage & audit

See where data came from and what reads it — end to end, automatically.

Search & discovery

Find the right table across the whole estate instead of guessing names.

Shared across workspaces

The same governed data is available to every workspace and every user who’s allowed.

🔀

Concept

The Metric View

In one line: the metric view is Databricks’ semantic layer — define a number like Total Volume or VWAP once, in one governed place, and dashboards, Genie and SQL all use that exact definition instead of re-inventing the formula.
📖
Think of it as the official rulebook for your numbers. Imagine ten people each work out “total revenue” their own way — you’d get ten slightly different answers and endless arguments. A metric view writes the rule down once: “revenue = this formula.” After that, everyone who asks for revenue gets the same number.
🧩

The problem it solves

Without it, every dashboard and analyst writes their own SQL for the same idea, and small differences make two reports quietly disagree.

One source of truth

Each metric’s formula lives in one place, so everyone gets the same number.

No repeated SQL

Define the joins and maths once; people just pick a metric and how to slice it.

Genie answers correctly

Ask “VWAP by country” and Genie uses the governed formula — it doesn’t guess.

Governed & consistent

It’s a normal Unity Catalog object, so permissions and lineage just work.

🔑

What’s inside: source, joins, dimensions & measures

A metric view points at a source, joins in the tables it needs, then exposes dimensions and measures on top.

Source

where the data comes from

The base table of trades the view is built on. Ours reads from trade_enriched — trades already joined to their market price and EUR values.

Joins

bring in other tables

Pull in dimension tables and give each an alias, with how it links to the source — e.g. dim_instrument as di on instrument_key. Dimensions then reference those aliases (di.commodity).

Dimensions

the ways you slice
  • Trade Date, Trading Season
  • Trader Company, Counterparty
  • Commodity, Country
  • Direction (buy / sell)

Measures

the numbers, with their formula
  • Trade Count — COUNT(1)
  • Total Volume — SUM(volume)
  • VWAP — volume-weighted price
  • Total Notional EUR — value in EUR
🔀

Coming from Power BI?

If you’ve built Power BI models, a metric view will feel familiar — here’s the mapping.

In Power BIMetric view equivalent
Semantic model / datasetThe metric view itself — but a governed Unity Catalog object, not locked to one report
DAX measure — Total Sales = SUM(...)A measure — Total Volume: SUM(volume), written in SQL rather than DAX
Fields on axes & slicersDimensions
Model relationships + Power Query sourceSource + joins
Certified / shared datasetEvery tool — dashboards, Genie, SQL — reads the one definition
Q&A (natural language)Genie

The big shift: your measures live in the catalog, not inside a single .pbix — so a dashboard, a Genie agent, and a raw SQL query all return the identical number.

📄

What it looks like

It’s written in a short YAML file: a source (with any joins), the dimensions, and the measures. A trimmed peek at this workshop’s energy_trading_metrics:

# energy_trading_metrics — written once, read everywhere
source: energy.energy_trading.trade_enriched

joins:                          # pull dimension tables in, give each an alias
  - name: dt                     # dim_time
    source: energy.energy_trading.dim_time
    "on": source.time_key = dt.time_key
  - name: di                     # dim_instrument
    source: energy.energy_trading.dim_instrument
    "on": source.instrument_key = di.instrument_key
  # …plus dtr (trader), dcp (counterparty), ddp (delivery point), dm (market)

dimensions:
  - name: Trade Date
    expr: dt.cal_date
  - name: Commodity
    expr: di.commodity
  - name: Direction
    expr: source.direction

measures:
  - name: Total Volume
    expr: SUM(source.volume)
  - name: VWAP
    expr: SUM(source.price * source.volume) / NULLIF(SUM(source.volume), 0)
  - name: Total Notional EUR
    expr: SUM(source.notional_value_eur)
    format: { type: currency, currency_code: EUR }
📊

The measures in ours

MeasureWhat it means
Trade CountTotal number of trades
